## 0. 能不能看到原版「脚本逻辑」的全貌？—— **不能，但能定点恢复**

### 0.1 为什么不能：三条实测依据

| # | 事实 | 怎么验证的 |
|---|------|-----------|
| 1 | **原版根本没有脚本**。`gamedata.pck` 2143 个条目里没有 `.lua`/`.js`/字节码；唯一的「脚本」是 `gfxscript/*.gbf`（22 个），那是**渲染着色器**，不含玩法逻辑 | `tools/r6pck.py list` + 全量内容扫描（上一轮已做完，见 `docs/original-readable/README.md`） |
| 2 | **可执行文件里没有任何名称信息**。`rich6.exe`（688 KB，2002 年 MSVC，4 节**未加壳**）里 **C++ 修饰名计数 = 0、`??`（RTTI）计数 = 0、无 PDB/DWARF、无有用导出表** → 没有函数名、类名、类型、变量名 | `grep -c '??' rich6.asm.txt` → 0；`pefile` 读节表（`.text/.rdata/.data/.rsrc`） |
| 3 | **现有反汇编只能用不能追**。`docs/original-readable/disassembly/rich6.asm.txt` 是**线性扫描**：把 `.text` 从头到尾当指令解，**没有函数边界、没有交叉引用** → 看到一行 `call 0x402430` 也不知道那是 fopen 还是别的 | 读文件头注释 + 抽查 |

**所以「原版脚本逻辑」这个东西在原版里压根不以可读形式存在** —— 它是一坨编译后的 x86 机器码。
上一轮 `docs/original-readable/README.md` 里也已经写过：「不能把参数表或二进制里的字符串当成这些算法的源码」。

### 0.2 能做什么：**定点逆向**（本轮已把工具补上并验证）

真正可行的工作方式是另一个 AI 恢复地图算法的那套：**拿一个确定的线索 → 反查谁引用了它 →
人工读那几十行汇编**。本轮把这个过程工具化了：

```
tools/r6_re.py          # capstone + pefile，自建「数据 ↔ 代码」引用索引
  info                  # 节表 + 指令数 + 调用目标数
  strs [-f 关键词]       # .rdata/.data 全部可打印字符串连同 VA（＝线索表）
  xref <VA|off:偏移>     # 谁引用了这个地址（push/mov/lea 的绝对立即数）
  dis <VA> --n 80       # 把某段反汇编出来给人读
  calls                 # 每个函数被谁 call（＝调用图）
```

**规模实测**：`.text` = 606 208 B，线性扫描得 **76 098 条指令**、**1 020 个直接 call 目标
（≈1 500 个函数）**。这个体量做**定点**恢复完全可行，做**全量**恢复不现实。

**独立复现验证**：拿另一个 AI 恢复出来的 8 个地图函数地址去查我的调用图 ——
**8 个里 7 个独立命中**，且调用关系与他们的描述吻合：

| 地址 | 他们说的功能 | 我的工具查到的 |
|---|---|---|
| `0x4030C0` | 曲线求值 | ✔ 被 **4** 处 call：`0x42bd1c / 0x42bd50 / 0x42bd84`（正好紧挨行走函数）、`0x42d084` |
| `0x42BC40` | 格间行走 | ✔ 被 3 处 call：`0x42bd3f / 0x42bd73 / 0x42bd8d` |
| `0x42B670` | 1×1 空地中心 | ✔ 被 2 处 call：`0x4264ea / 0x42756d` |
| `0x42B700` | 同上（多格） | ✔ 被 4 处 call |
| `0x42C250` / `0x42C080` | 读地产块 / 读曲线道路 | ✔ 各被 1 处 call（`0x42c7d4` / `0x42c7dc`，相邻） |
| `0x402F20` | 曲线内部 | ✔ 被 1 处 call（`0x40316a`，就在 `0x4030C0` 里） |
| `0x42EE10` | 小地图变换 | ✘ 不在直接 call 目标里（应为间接调用/跳转表） |

**再给一个本轮新做的例子**（证明确实能读通原版玩法代码）：
`config/card.txt` 的字符串 VA = `0x49df4c`，`xref` 命中**唯一一处** `0x41e78f`。
从那儿反汇编出来就是**卡片表的加载函数**：

```
0x41e78f  68 4c df 49 00   push 0x49df4c        ; "config/card.txt"
0x41e794  e8 97 3c fe ff   call 0x402430        ; fopen
0x41e7b3  e8 68 44 fe ff   call 0x402c20        ; fgets(buf,256,fp) ← 读第一行「42」
0x41e7be  33 ff            xor edi, edi
0x41e7c0  85 c0            test eax, eax
0x41e7c2  7e 40            jle 0x41e804         ; [esi+0x6d60] = 卡片数量
0x41e7c7  55               push ebp
0x41e7c8  6a 10            push 0x10            ; ← 每行最多 16 字节（卡名）
0x41e7d2  ...              call 0x402c20        ; fgets(buf,16,fp)
0x41e7eb  e8 a7 7f 06 00   call 0x486797        ; 拷进记录
0x41e7fa  81 c3 30 02 00 00  add ebx, 0x230     ; ← 每条卡记录 = 0x230 = 560 字节
0x41e800  3b f8            cmp edi, eax
0x41e802  7c c3            jl  0x41e7c7         ; 循环 42 次
```

**顺带得到一个我们原先不知道的硬数据：原版卡片记录结构体大小 = 560 字节**，
第一行是数量、后面每行是不超过 16 字节的卡名。
