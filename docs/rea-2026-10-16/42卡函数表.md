# 42 卡的效果函数表 —— 挖到了（2026-10-16）

> C14 一直缺一块：**每张卡的原版效果函数在哪**。
> 报告只给了零星几个地址（暴走 `41f970`、查封 `420350`…），没有完整表。
> 本文把**整张表**挖出来了，**42/42 全**。
>
> **证据**：`card-registry-disasm.txt`（`tools/r6_disasm_range.py 0x420000 0x424000` 的反汇编，5758 行）
> **产物**：`game/data/rules/card_functions_native.json`

## 1. 怎么找到的

`FUN_004209c0`（清除卡效果）在 Ghidra 里**调用点为 0** —— 因为它**只被函数指针引用**，
没有直接的 `CALL` 指令。于是换个思路：**直接在 exe 里搜「指向它的 4 字节值」**
（`tools/r6_disasm_range.py`），一击命中。

`0x004209c0` 只出现 1 处，落在 `0x00422823`，而周围**是一串整齐的注册序列**：

```asm
00422823  mov  dword ptr [eax + 0x21c], 0x4209c0     ; ← 清除卡的效果函数
0042282d  call 0x41f040                              ; 
00422832  push 0x27                                  ; 下一张卡的卡号
00422834  mov  ecx, esi
00422836  mov  dword ptr [eax + 0x224], 0x4220a0     ; ← 同一张卡的第 2 个函数
00422840  call 0x41f040
```

**读出来的结构**：原版给**每张卡注册两个函数指针**，存在卡片对象的
**`+0x21c`** 和 **`+0x224`** 两个字段里（卡号 **0 基**，`0x26=38` 正是清除卡）。

## 3. 两个值得注意的规律

1. **`+0x21c` 的顺序 = 卡号顺序**（`0x41f1a0` 一路递增到 `0x420ad0`），
   而 **`+0x224` 的函数是「紧挨着排」的第二组**（`0x420f70` → `0x422160`）。
   → 说明原版是**两张并行的函数表**，按同一卡号索引。
2. **无敌卡（26）和隐形卡（41）共用同一个 `+0x224`（`0x421820`）** ——
   两者都是「给角色加一种保护状态」，共用判定很合理 ✅
   **`+0x224` 很可能就是「这张卡能不能用 / 门禁判定」**（正是 C14 要找的东西）。

## 4. ⚠️ 顺带纠正我上一轮的一个错误结论

上一轮我把 `420350`（查封）和 `420550`（诱拐）算成「**落在 `FUN_004202a0` 内部**」，
依据是「用下一个函数入口当边界推算」。**这是错的** —— 本表证明它们是**各自独立的函数入口**。

**根因**：**Ghidra 没有把这些函数识别成函数**，因为**它们只被函数指针引用、没有直接 `CALL`**。
所以 `getFunctionContaining()` 返回空，我的 `DecompileAt.java` 会报「不在任何已知函数内」并跳过。

> **教训**：**「用入口区间推算归属」不可靠**；判断某个地址是不是函数入口，
> **要看它有没有被 `mov [xxx+off], <addr>` 这样注册过** —— 这类「函数指针表」
> 在原版里很常见（卡、宠物技能、状态处理都可能是）。
>
> **待办**：`DecompileAt.java` 要改成「查不到函数时，直接按地址线性反汇编」，
> 否则后面反编译这些卡函数会**全部被跳过**。

## 5. 对 C14 的意义（下一步怎么用）

有了这张表，C14 的「**逐卡核行为**」终于可以系统地做了：

1. **门禁**：反编译每张卡的 **`+0x224`** 函数 → 看它在什么条件下返回失败
   （这正是报告里说的「人工选择、范围、失败耗卡、锁牌与容量」）
2. **效果细节**：按需反编译 **`+0x21c`**（如 C09 已做的清除卡）
3. **优先级**：先做**用户最常碰到的**（步卡、骰子、四神、购地、清除、路障/地雷）
