## 二、需要你决策的议题（按建议优先级排序）

### 议题 1 —— `.r6m` 地块坐标表要不要继续逆？（影响：坐标精度）

> ⚠️ **2026-09-25 更新：本议题已解** —— `offset 504` = 街区数、`512` 起是**地产块表**
> （记录长 `48×A+76`），已与 `.r6s` 交叉验证。详见 **§十**。
> 但**它不是「第几格 = 哪个坐标」的点表**，只是**街区矩形范围**，
> 所以棋盘 111 格仍走「红框锚点 + 样条重建」这条兜底路径（原因见 §十）。

**现状**：`.r6m` 头部的参数已经全部读出，但**偏移 576 之后约 32 KB 的疑似地块表没能解出**
字段语义（只能看出是 16 字节一组的循环记录）。所以地块坐标改用「红框锚点 + 样条重建」。

**为什么拿不准**：重建结果肉眼与原版路径吻合，但它是**等弧长均匀重采样**，
原版的实际格距并非完全均匀（实测格距 3.12~4.38，差 40%）。也就是说：
- 视觉上没问题；
- 但如果后面要做「按格精确对齐建筑/事件的摆放位置」，这点误差会显出来。

**选项**：
- **A. 先不动**（推荐）：视觉已达标，把时间花在玩法上。等真出现对齐问题再回来逆。
- **B. 继续投入**：再花一轮逆向 `.r6m` 576~33000 段（需要拿 `china.r6m` 等做交叉比对，
  对比不同地图字段变化来定位语义）。
- **C. 换路子**：直接在**原版里跑一遍、逐格截图反推格心坐标**（工作量大但结果绝对真实）。

### 议题 2 —— 其余 7 张地图没有棋盘美术，怎么办？（影响：可玩地图数）

**现状**：核实过整个 `gamedata.pck` —— **只有埃及（aiji）有 `ditu*.tga` 这张 1024² 俯视棋盘图**。
`china / island / japan / paris / train / space / trybuild` 都没有。
它们现在会走**兜底布局**：一块纯色沙地平面 + 程序生成的矩形地毯环
（见 `.workbuddy/tex/_china_check.png`），并且小地图**不叠加**路径/地块（因为对不上）。

**为什么拿不准**：原版这些地图的地形是 3D 网格（在 `.r6s` / `.pol` 里），
不是一张贴图。要还原就得解网格格式（见议题 3）。

**选项**：
- **A. 只做埃及**（推荐先这样）：把埃及当唯一"精装"地图，其余 7 张保留兜底版式，
  在选图界面标注「(简化地形)」。
- **B. 解 `.r6s` / `.pol` 网格**：一次性解决 8 张地图的地形 + 河床起伏（工作量大，见议题 3）。
- **C. 反推**：跑原版进每张地图截俯视图，拼成新的 1024² 贴图（8 张 × 若干帧，机械但可靠）。

### 议题 3 —— 要不要解 `.pol`（R6HS）/ `.a_q`（IDP2）？（影响：地形起伏 + 原版角色模型）

**现状**：
- `aiji.pol`（365 KB，magic `R6HS`，第 8 字节起是对象名 `Plane01`）→ **没解**。
  它是地形/建筑的真实 3D 网格。解出来地形就能有**河床高低、土丘起伏**，
  而不是现在这块平面。
- `actor/role*/**.a_q`（magic `IDP2`）→ **没解**。这是角色的骨骼网格。
  所以现在角色是**程序化 chibi**（胶囊躯干 + 球头 + 两条手臂 + 地面圆盘），
  配色用原版 `Sim.PLAYER_COLORS`，**不是**原版模型。

**为什么拿不准**：两个格式都要靠"猜结构 + 试渲染"来逆，没有文档；
属于投入产出不确定的活。

**选项**：
- **A. 暂时保持程序化角色**（推荐）：chibi 已能辨认归属，先把 42 张卡牌等玩法补齐。
- **B. 只解 `.pol`**：优先拿地形起伏，视觉收益最大。
- **C. 都解**：视觉最完整，但可能吃掉好几轮时间。

### 议题 4 —— 房屋精灵的「街道 → 风格组」对应关系 + 建筑类型（影响：地产外观）

**现状**：`game/assets/uitex/house/` 有 54 张房屋精灵，命名规律已确认：
`<风格组 a/b/c/d/e><建筑类型 01/02/03><等级 01~07>`。
埃及地图目前**统一用 a 组 + 类型 01（住宅）**，等级按 1~5 取图。

**为什么拿不准**：
- 「哪条街用哪一组风格」**没从原版配置里找到**（`aiji.txt` 只给了
  `industry 1 / shop 1 / uptown 1` 三个开关，没给街道映射）。
- 而且现在 `Sim.act_buy()` 把**所有地都记成 `type = "uptown"`**，
  原版是分 **住宅 / 商店 / 公司** 三种的（造价与租金都不同，我们 `realtime.json` 里
  也只锚定了"公寓"一档）。

**选项**：
- **A. 保持现状**：全部 a 组 + 住宅，先在决策文档里记着。
- **B. 按街轮换风格**：用 `street_index % 5` 分配 a~e 组，至少视觉上有区分
  （纯装饰，不涉及数值）。
- **C. 补建筑类型**：把 住宅/商店/公司 三档的造价与租金从原版数值表里挖出来，
  做成真正有区分的玩法 + 对应 `01/02/03` 三套外观。**这条会改到玩法数值，需要你点头。**

### 议题 6 —— 小地图叠加层的精度（影响：很小）

**现状**：小地图底图用原版 `uitex/subc/m_<map>.png`，**地块 UV → 像素是线性映射**。
实测过：把地块 UV 直接乘图宽高，点位精准落在那条深色路径上
（验证图 `.workbuddy/tex/_mm_check.png`）。
但对齐仍有 **约 3~10 px 的残差** —— 因为我们的路径本身是重建的（议题 1），
不是逐格精确的。

**为什么拿不准**：这是议题 1 的从属问题，单独修不划算。

**选项**：
- **A. 接受**（推荐）：小地图上路径、地块点、玩家点是**同一套映射**，
  自洽；只是与底图那条装饰路径略有偏差。

### 顺手修掉的一个真 bug

`_building_spot()` 的注释写「近端边缘贴在地毯边线 + 空隙上」，但原公式
`dist = fp*BUILDING_SCALE/2 + BUILDING_GAP` 算出来近端边缘离地块中心只有 **0.18 地毯**
（地毯半宽是 0.47）→ **建筑压在自己地毯上**，与注释矛盾。改成真正的近边锚定：

```
half = fp * BUILDING_SCALE / 2                          （建筑半宽）
dist = (RUG_HALF + BUILDING_GAP + half) * 地毯边长        （RUG_HALF = 0.5）
→ 近端边缘恒在 RUG_HALF + BUILDING_GAP 处，**与 fp 无关**
```

### 已确认（新证据）

1. **索引块定位是对的**：a0101 `model.pol` = 144 头 + 91×32 顶点（末 3056）

2. **法线不是 `(f0,f6,f7)` 也不是 `(f4,f5,f6)`**：把每个字段的值域拉出来看，
   `f0 / f6 / f7` 的取值几乎只有 **{0, ±1}**（如 v0 `f0=1,f6=0`；v2 `f0=-1,f6=1`）

3. **`f4/f5` 是「平面/盒投影」而不是展开 UV**：拿同一面的一条竖边比对 ——
   `v0` 与 `v4` 只差 y，**f4 完全相同（0.6249）而 f5 从 0.0757 变到 0.3528**；
   `v1/v5` 同样（f4 恒 0.1907）。即 **f4 = f(x,z)、f5 = f(y)**。

   **UVW Map（Box）修改器** gizmo 名，盒投影正是这个行为。
4. **打包环节不是元凶**：`tools/bld_sheet.py` 对 a0101 / a0201 / a0304 / d101
   四栋做「原始 `.tga` vs 工程 `.png`」逐张对照，**两列几乎一模一样**

## 10.6 议题 34 —— 画面对齐收尾

### 34-★ 老板 2026-09-25 报的「地毯与石子路完全没对齐」—— 根因已定位并修复

**症状**：实机近景里，地毯（地块贴花）与石子路（步道）**整体错开约 2 格**，
远处看「形状像，但就是不在路上」。

**根因（不是格数问题）**：`game/scripts/ui/board_view.gd` 的 `_build_ground()`
把地面平面的 UV 写成了

```gdscript
uvs = [Vector2(0,1), Vector2(1,1), Vector2(1,0), Vector2(0,0)]   # v = 0.5 - z/S
```

即**整张地形贴图沿 Z 轴被镜像**。而地块坐标 `aiji_tilepos.json` 的映射是
`py = (z/S + 0.5) × 1024`（与 z **同向**）。
因为路线是**闭合环且大致围绕棋盘中心**，「旋转 180°」与「沿 Z 镜像」在环上
**几乎等价** → 症状不像翻转，而是「形状对、整体错开」。

**修复**：改成 `v = z/S + 0.5`（Godot 的 `uv.y=0` 在贴图上方，与 `Image` 第 0 行一致）。

**修复后的验证（三层，都可复跑）**
1. **2D**：`tools/route_from_walkway.py` 的验收叠图 `docs/orig-scene/aiji_route_walkway.png`。
2. **3D 直接标定**：把 94 个格点的像素位置画成洋红十字/彩圈写进
   `assets/terrain/aiji_ground.png` 再截图 → 地毯**正好落在标记中心**（不是"差不多"）。
   ⚠️ 改贴图后**必须** `godot --headless --path game --import`，否则 `.godot/imported/*.ctex`
   还是旧图（这一坑骗过我们一次）。
3. **对齐指标**（`tools/walkway_mask.py --tex ditu`）：

   | 指标 | 修复前 | 修复后 |
   |---|---|---|
   | 格点 → 步道掩码（任一点） | 中位 6.9 px | **中位 0.4 / 90% 4.9 / 最大 12.8 px** |
   | 格点 → 步道**中心线** | 中位 20.3 / 90% 43.2 / 最大 65.2 px | **中位 5.0 / 90% 16.0 / 最大 27.9 px** |
   | 离中心线 > 25 px 的格 | **45 / 111** | **1 / 94** |

**同源坑（一并修掉）**：`game/scripts/ui/minimap.gd` 的 `_uv()` 里也有 `0.5 - w.y/b`。
判定工具 `tools/check_minimap_uv.py`（HUD 是小地图美术，颜色被重画过，


# 12. 2026-09-25 追加：UI 对齐收尾三修（GO 钮 / 是-否胶囊 / uishot 抓帧）

## 12.1 ⭐ GO 钮是**两张贴图叠出来的**（推翻「只用 labar/go.png」）

原版角色头顶那颗「GO」不是一张图：**`labar/背景.png`（深蓝球）打底 +
`labar/go.png`（青球 + GO）叠在偏右上**。单独用任一张都不对，因为两张**都是贴边裁切的残图**：

| 素材 | 尺寸 | 可见区 alpha bbox |
|------|------|------------------|
| `labar/背景.png` | 64×64 | `(0, 3, 64, 64)` —— 左右贴边，直径就是 64 |
| `labar/go.png` / `go_dn.png` | 64×64 | `(0, 10, 41, 64)` —— **左侧被裁**（"G" 缺一竖） |

**因为都贴边，不能按画布对齐，只能按「可见区中心」对齐。** 参数从原版实机
`docs/screenshots/orig/08_牌桌_2.png` 按颜色分离量得（截图是 native 的 1.5 倍）：

- 蓝球直径 ≈ **73.3 native** → 贴图 64 缩放 **×1.146**
- 青球可见区中心 比 蓝球可见区中心 偏 **(+13.7, +1.0) native**

→ `tools/make_panel_ui.py::_compose_go()` 合成 `go_btn.png` / `go_btn_dn.png`（78×78 native），
`app.gd::UI_GO_SIZE` 42.7 → **78.0**。原版截图里 GO 旁边那颗**实体骰子**是 `labar/骰子.png`
（我们走 3D `Sprite3D`），**不是**这张合成图的一部分。

## 12.2 是 / 否 = **两块半胶囊拼一整颗**

`yes_up.png` / `no_up.png` 都是 64×32、**可见区只有左边 56×32**（右 8px 全透明）；
`yes` 只有**左**圆头、`no` 只有**右**圆头 → 并排贴紧才是原版那颗「是│否」胶囊。
之前用 `KEEP_ASPECT_CENTERED` + 40×20 native + 8px 间距 → 屏幕上两颗**半胶囊各自为政**
（直切口外露）。现在：

- `AtlasTexture.region = (0,0,56,32)` 裁掉透明边；
- `row.separation = 0`；
- `STRETCH_SCALE` + 56×32 native（素材 1:1）；
- ⚠️ 不能用 `KEEP_ASPECT_*`：容器给窄时会把胶囊裁掉一半（实测）。

⚠️ **未考证**：原版把这两块画多大（没找到带买地提示的原版截图）→ 已登记在
`docs/ui-audit.md §8`。

## 12.3 ⭐ `--uishot` 的两个坑（为什么之前「GO 钮没画出来」）

1. **不能按固定时刻拍**：开局头几秒角色还在「入场」状态（`me.moving != 0`），
   `_sync_action_entry()` 此时把 `_go_btn.visible` 置 **false** —— 3.0 秒硬拍只能拍到
   头上那颗骰子。→ 改成**等 `_go_btn.visible` 真为真**再拍（8 秒兜底 + `push_warning`）。
2. **`_capture()` 是协程，必须 `await` 它之后才改游戏状态**：它内部
   `await RenderingServer.frame_post_draw` 才去 `get_viewport().get_texture()`。
   原代码 `_capture(...)` 没 await 就紧跟 `Net.send_action("roll")` → 角色先动起来、
   下一帧把 `_go_btn.visible` 置回 false → **真正抓帧时按钮已经没了**。
   症状很迷惑：诊断里 `get_global_rect()` 完全正确、图里却空无一物。

## 18.1 ⭐ 传送平台「掷 1 点留在原地」—— 两个原因叠在一起

**先摆数据**：埃及的 2 格传送平台是**索引 24 / 25**（路径上前后脚），但
`aiji_tilepos.json` 里它们的**世界坐标相隔 13.90 单位**（正常相邻格距 ≈5）
→ 这两格之间路径"跳"了约 3 格，正是**一座传送门的两端**该有的样子。

**原因 ①：只有「停下」才判传送。** 传送原来写在 `_resolve_event` 的 `platform` 分支里，
而 `_resolve_event` 只在 `_arrive`（`moving` 归零那一刻）被调用 →
**「路过」传送平台不触发**，于是玩家可能**停在**传送平台上。

**原因 ②：两格平台互为目的地。** `_other_platform(idx)` 返回「第一个不是 idx 的 platform 格」，
于是 24 ↔ 25 对称互传。

**两者一叠加**就是老板遇到的现象：
1. 玩家停在格 24 上（原因 ① 的产物）
2. 掷 1 点 → 走 1 格到格 25（传送门的另一端）
3. `_arrive(25)` → 被传回 24 → **看起来原地没动**

**修法**：

| 位置 | 改动 |
|---|---|
| `_other_platform()` | **跳过路径索引相邻的 platform 格**（`_tile_distance <= 1`）—— 相邻的两格就是**同一座传送门**，不是「另一处」。埃及因此不再互传；别的图若真有相距很远的 2 处平台，仍然正常传送 |
| `_advance()` 逐格循环 | 新增「**经过即传送**」检测（与路边物体、陷阱同级），并 `moving = 0` 结束本次移动 |
| `p["_teleported"]` | 新标记：同一段行走内不再被传送（防 A→B→A 死循环）；`_arrive` 之后复位 |
| `_resolve_event` 的 platform 分支 | 退化为「刚好停在上面」的兜底，且本段行走已传过就跳过 |

**为什么「不互传」是对的**：这两格在路径上相邻、世界里隔 3 格 —— **「传送」这件事已经体现在
路径本身了**（走过去就是被传送过去）。把它们当成互为目的地，只会让玩家在两端之间来回弹。

⚠️ 登记为**仍有不确定**：原版传送平台的**完整语义**（能否双向、传送后是否继续走完剩余步数）
没有明文依据 —— `Info.txt` 里没有任何「传送」文案，`aiji.r6s` 里**没有 platform 场景节点**，
只有 `Roadevent.txt` 的一行名字。现在的实现取「最不会打转」的那个。

## 20.3 ⭐ 掷骰节奏：先抛骰子定格，角色才走

**原来的做法**：`act_roll` 里一设 `moving = n` 角色立刻开始走，UI 只是「同时」播骰子动画
→ 老板说的「点击 GO 角色就直接走了，同时骰子显示数字，节奏错误」。

**改法**：在 `Sim` 里加一个「掷骰动画时长」的闸门：

```gdscript
const ROLL_ANIM_SECONDS := 1.15        # 与表现层的 DIE_FLY_TIME 对齐
...
p["moving"] = n
p["move_after"] = time + ROLL_ANIM_SECONDS   # 动画播完之前不许起步
```

`step()` 里按帧切分：

```gdscript
var t_before := time
time += dt
...
var seg: float = time - maxf(t_before, float(p.get("move_after", 0.0)))
if seg > 0.0:
    _advance(p, seg)          # 只走「本帧里动画终点之后」的那一段
```

⚠️ **踩的坑**：第一版写成「`wait <= 0` 就走整个 `dt`」，于是**跨过动画终点的那一帧
把等待的 1.15 秒也算进了移动距离**（自检直接抓到：期望走 0.5 格，实际走了 1.65 格）。
必须用「本帧区间」和「动画终点」**取交集**。

好处：**远端玩家也会看到同样的节奏**（因为闸门在权威 Sim 里，不在 UI 里）。

# 21. 2026-09-26（下午九轮）卡片栏规则：上限 5 / 同种叠加 / 顶最前方 / 锁定保护

老板：

> "现在的卡片系统也还是不对哦，卡片栏最多有五张卡（同样的卡可以叠加，只占一个栏位），
> 然后新加入的卡会将最前方的卡片顶掉，可以通过锁定让卡不被顶掉。"

## 21.1 依据：配置里**没有**这一项，老板的实机观察就是权威

翻遍 `Initvar_r.txt`（整张表只有 25 个 `Card_*` **效果**参数），**没有手牌上限**；
`Info.txt` 里也没有「卡片已满」之类的文案。

唯一相关的是 **`Card_FuShen_NumCard = 5`**「使用福神卡得到 5 张卡片」
—— 一次能拿 5 张，与「上限 5」自洽（如果上限小于 5，这行数据就没意义）。

→ **实现依据 = 老板的原版实机观察**，常量上直接标注来源。

## 21.2 实现

**`Sim`（权威层）**：

```gdscript
const HAND_MAX := 5      # 卡片栏最多 5 张；同种叠加只占一个栏位

func hand_slots(p) -> int          # 占了几个栏位（同种只算一个）
func _push_card(p, card_id)        # 统一的「加一张卡」，返回 {added, dropped, reason}
func act_lock_card(id, card_id)    # 锁定 / 解锁（菜单 id 2）
func card_locked(p, card_id) -> bool
```

`_push_card` 的规则：
1. **同种已在手** → 直接叠上去（`cards` 里多一个元素，**不占新栏位**）
2. 是新种类、栏位已满 → 从**最前方**（获得顺序的第一个）往后找**第一张没锁定的**顶掉
3. **全锁着** → 加不进来（`reason = all_locked`）；买卡时**退还点券**

**四个加卡点全部改走它**：`_give_random_card`（卡片点/卡片商店送卡）、`act_buy_card`、
抢卡卡（`seize`→ 偷对手一张）、福神卡（一次给 N 张）。

**锁定状态从 UI 挪到权威层** —— 这是关键：原来 `_card_locked` 是**客户端本地字典**，
而「顶卡要跳过锁定的」这个判定发生在 `Sim` 里，本地字典服务端根本看不到。
现在存 `p["card_locks"]`，新增 `net.gd` 动作 `lock_card`，UI 从 snapshot 读。

**手的顺序变成有意义的** → UI 的 `_sync_card_hand` **去掉了 `cards.sort()`**
（原来为了「同种聚在一起」排序，那会打乱「最前方」的定义）；
同种合并也改成「**按首次出现顺序去重**」（原来的「相邻相同才合并」依赖排序）。

## 24.1 ⭐ 同格「挤人」

原版**不允许多人站在同一格**：后到的人把先到的人**往前挤一格**。
「挤」是一种**搞怪**：被挤的人**要付房租**，但**不触发**地面事件 / 买地 / 升级。

实现（`Sim._push_away_occupants()`，在 `_arrive()` 的**最开头**调用）：

```gdscript
for oid in player_ids():            # 同格、站着不动（moving == 0）的人
    var dest := _wrap(here + 1)
    o["tile"] = dest
    _ev("push_away", o, {"by": id, "name": p.name, "from": here, "tile": dest})
    if map.tile(dest).kind == "plot":
        _resolve_plot(o, dest, t)   # ← 走一遍地产结算：**会付房租**
        _clear_chance(o)            # ← 买地 / 升级的机会**当场作废**
```

**为什么这样切最省事**：`_resolve_plot` 本来就负责「收租 / 给买地机会 / 给升级机会」，

# 26. 2026-09-26（下午十四轮）修 bug：切到股票页后功能区按钮「消失」

## 26.1 根因：**VBoxContainer 重新布局把按钮条顶上去了**

右下角功能区是个 `VBoxContainer`（`_br_box`）：

```
_br_box (VBoxContainer)
├── mp            ← 地图面板（小地图在里面）
└── _icon_bar     ← 6 个功能按钮
```

`_sync_br_pages()` 里我原来写的是：

```gdscript
_br_map_panel.visible = on and _br_page == 2      # ❌ 非地图页就把整个面板隐藏
```

**面板一隐藏，VBox 立刻重新布局** → `_icon_bar` **上移到原来 `mp` 的位置** ——
而那一块地方正是**股票页浮着的地方**，于是按钮条被股票面板整个盖住 → 「按钮都没了」。

（`mousedown` 也点不到：股票面板的表格行是可以点的，等于把按钮的点击一起吃了。
「再也切不回去」就是这么来的。）

## 26.2 修法：面板**始终占位**，只把「内容 + 底框」换掉

```gdscript
_br_map_panel.visible = on                       # ✅ 永远可见（占住 VBox 里的位置）
var on_map := on and _br_page == 2
_minimap.visible = on_map                        # 只藏里面的小地图
_br_map_panel.add_theme_stylebox_override("panel",
    _br_map_sb if on_map else StyleBoxEmpty.new())   # 别的页就把底框透明化，别露出深蓝底
```

另外两道保险：
- `_hud.move_child(_stock, 0)` —— 把股票面板压到**最底层**，保证按钮条永远在它上面
- `StockPanel._bg` 的 `mouse_filter` 本来就是 `IGNORE`（只有表格行吃点击）

## 27.1 ⭐ 修的第一个缺口：**客户端收不到任何事件**（toast / 音效 / 语音全无）

`Sim._ev()` 的实现是 `game_event.emit(...)` —— **只在本地发信号**：

| 谁 | 有没有事件 |
|---|---|
| **房主** | ✅ 有（他自己的 UI 连着 `Net.sim.game_event`） |
| **客户端** | ❌ **完全没有** —— 客户端的 `Sim` 只是**回放快照**（`apply_dict`），不会自己产生事件 |

**也就是说：联机时客机从头到尾一声不响、一个提示都没有。**（单机测不出来，只有真的开两个进程才发现。）

**修法**（`net.gd`）：房主把事件 RPC 出去，客户端收到后在**本地重新 emit** ——
这样 `ui/app.gd` **一行都不用改**（它连的一直是 `Net.sim.game_event`）：

```gdscript
@rpc("authority", "call_remote", "reliable")
func _rpc_event(kind: String, data: Dictionary) -> void:
	if sim != null:
		sim.game_event.emit(kind, data)

# 房主侧（_internal_start 里）：
if is_host and has_remote_peers():          # ⚠️ 单机时别发，否则报 "RPC on yourself"
	sim.game_event.connect(func(kind, d): _rpc_event.rpc(kind, d))
```

## 27.5 排查过程踩的坑（值得记）

1. **`_fail()` 用 `push_error` 在 headless 下不进 stdout** → 失败时日志一片空白，
   排查半天。**改成先 `print` 再 `push_error`**。
2. **`(x as Dictionary).get(...)` 后面直接点成员**（`.is_empty()`）在 GDScript 里**编译不过**，
   必须**先落到一个 `Dictionary` 变量**再调。
3. **快照里 `casino` 的 key 是 `int pid`**，用 `str(id)` 查会**永远查不到**。
4. **别缓存 `client_id`** —— 房间成员会随重连变化，缓存下来的 id 不在 `players` 里时，
   读出来全是空、白等满 12 秒超时。**每轮重新取**。
