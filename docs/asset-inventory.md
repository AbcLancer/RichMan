## 4. `.pol`（R6HS）网格格式 —— 本轮定案

```
0     char[4]   "R6HS"
4     u32       版本：100 = 单体模型 / 200 = 地形（Plane01）
8     char[32]  对象名（Blender 名）
40    f32[16]   4x4 变换矩阵（单体模型均为单位阵）
104   u32       标志
108   f32[3]    包围盒中心
120   f32       包围半径
124   u32       顶点数 nv
144   record[nv]  顶点记录，**步长 32 字节 = 8 个 float**
```

顶点记录 8 个 float 的语义（**本轮的成果**）：

| 序号 | 含义 |
|---|---|
| f0 | 面级常量（0 / ±1 / ±0.65 / ±0.75），**不是** UV |
| f1 f2 f3 | 位置 x y z（Y 朝上，脚底 ≈ 0） |
| f4 f5 | ❌ **曾被当成 v/u，2026-09-26 证伪**：见下方警告 |
| f6 f7 | 面级常量 |

> ⚠️⚠️ **`f4` / `f5` 不是 UV**（2026-09-26 修正）。
> 原先根据「a0101 前墙取 (f5,f4) 后大致落在某个图块上」下的结论**站不住** ——
> 改用**量化判据**：比较同一三角面在 3D 空间与 UV 空间的三个内角之差，
> 真正的 UV 应 < 8°，随机数据约 40–60°。实测 `(f4,f5)` / `(f5,f4)` / 6 种翻转组合
> **全都落在 45.9°（中位 40.7°）= 随机水平**。
> 同样被否定的还有「分离式 UV 数组」（144+24·nv 起 8·nv 字节，61.5% 的值落在 [0,1] 之外）。
> 所以 `pol2obj.py` 里 `uv = stack([raw[:,5], raw[:,4]])` 这一行是**错的**，
> 连同它之后的 `snap_uv_to_content()` 吸附 hack 一起，都是**在掩盖问题**。
> ➡️ 建筑贴图错乱的根因在此，**尚未解决**。下一步最有希望：包里每个建筑目录都带
> **`.max`（3ds Max 源文件）**，可从那里反查 UVW。详见 `docs/decision-log.md`「议题 20」。

顶点块之后是一段**变长材质块**（起始 12 字节 = D3DMATERIAL 的 Diffuse/Specular/Power，
后面跟着贴图名与 `refractionMap` 等参数），再后面是：

```
?     u32         三角形数 tc
?+4   u16[3*tc]   索引（三角形列表，非 strip）
```

索引块位置**不能写死**，必须扫描「u32 tc + 3*tc 个 u16 且全部 < nv」这一模式并取 tc 最大者
（`tools/r6pol.py::find_index_block`，115 个文件全部命中）。

### 已知遗留

原版 UV 是 3ds Max「Flatten Mapping」打包过的结果，**我们只能取回约 73%**
（实测：8233 个顶点里 6046 个落在图集有效图块上）。剩下的落在图集空白底上。
处理办法（`tools/pol2obj.py`）：

1. `snap_uv_to_content()` —— 把这 27% 的顶点 UV 吸附到最近的有效图块像素；
2. `bleed_atlas()` —— 对图集做边缘外扩（texture bleed），任何 UV 都能采到合理颜色。
