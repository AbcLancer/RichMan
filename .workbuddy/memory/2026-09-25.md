**项目目标（老板原话）**：复刻《大富翁6》，重点是**即时制玩法**；先复刻 + 实现正常联机，

**本体位置**：`F:\游戏\Rich6`（软星 2002 繁体中文版）

### 完成事项

1. **破解 `gamedata.pck` 资源包格式**（371 MB / 2143 文件）—— 完整逆向成功。
   - 格式：`"PCK\0"` + u32 + 目录项数组（**固定步长 264 字节**）+ 连续未压缩数据区
   - 条目尾部 8 字节 = `[pad u8][u32 offset][u24 size]`，名字 GBK 从 `entry_base+1` 起
   - 校验依据：`off+size == next_off`，2143 项 **0 处断裂**
   - 工具：`tools/r6pck.py`（info / list / extract，仅标准库）
   - 详见 `docs/pck-format.md`

2. **确认素材可直接复用**：TGA `type=2` 真彩 RGBA，中文名 GBK 解析正常，
   导出后 Pillow 读取 + 视觉确认无误。含 `.psd`(97)/`.max`(78) 美术源文件。

3. **玩法数值几乎全明文**：`config/Initvar_r.txt`（即时制）与 `Initvar_t.txt`（回合制）
   对照，`House.txt`（6 类建筑×等级租金公式）、`Card.txt`（42 卡）、`Role.txt`（12 角色 AI 性格）、
   `Roadevent.txt`（16 事件点）、`Pet.txt`（9 精灵）、`Info.txt`（84 KB 文案）。

4. **定位「联机用不了」的根因**：
   - `rich6.exe` 导入 `WS2_32.dll`（原生 Winsock，**非 DirectPlay**），
     含 `accept/bind/connect/listen/sendto/recvfrom/select/WSAAsyncSelect` + `gethostbyname`
   - → 当年有**官方大厅服务器**（需域名解析），**早已停服** = 联机失效根因
   - → 结论：联机不是「修复」，而是「重做」，可放手按现代标准设计

5. **发现进程内就是 C/S 架构**：`r6log.txt` 显示 Server（逻辑）+ Client（表现）
   用 `clmsg_*` 消息通信 → **玩法与网络本就解耦，换网络层不必动玩法**。

→ 改为「Write 工具写 UTF-8 临时文件 → Python 转码 GBK」绕开 heredoc。

**测试方法**：`cmd //c PLAY.bat` → sleep → `tasklist //FI "IMAGENAME eq ..."` 确认进程起来 → `taskkill` 关掉。

### 结果：拿到了原版全流程真实截图

**最重要的三条发现**：

1. **牌桌是一整块连续 3D 地形**（沙丘、河道、碎石路、棕榈、3D 建筑），
   地块是**铺在地面上的贴花**（波斯地毯图案），相机是**低机位强透视斜视**。
   当前工程做成「平的矩形外圈 + 独立方块格 + 悬浮文字标签」，观感自然完全不对。
2. `.gbf` 文件其实是 **DirectX 8 effect 纯文本**。`terrgeom.gbf` 显示地形 =
   **双贴图 MUL + 顶点色(PRIMARY)** → 地形靠**顶点色逐格着色**，不是几百个地块对象。
3. `samples/scene/aiji/` 里有 **1024×1024 完整地形贴图** `ditu.tga` / `ditu2_1024.tga`
   （编辑器版用红框标出每个地块槽位）→ **棋盘美术可以直接复用**，
   地块坐标可用 `tools/extract_plot_uv.py` 从红框自动提取（已验证，埃及检出 50 个）。

### 怎么把原版跑起来的（踩坑记录）

- **沙箱禁止修改工作区外的既有文件**：`F:\游戏\Rich6\init.txt` 覆写 / 重命名全部 `PermissionError`，
  但**新建文件允许**（`WriteAllBytes` 也拒绝，`Create new OK`）。F: 是 exFAT、DACL 为空，与权限无关，
  纯粹是沙箱策略。→ 用 `tools/make_r6_runtime_copy.py` 造了**可写运行副本** `F:\游戏\Rich6run\`
  （pck 硬链接失败被沙箱拦，回退实拷贝，共 615 MB），在那里改窗口化配置。
- **进程保活**：用 `DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP` 启动的进程会被回收；
  改由**后台常驻的 keepalive 进程持有游戏子进程**，游戏才能跨工具调用存活。
- **不要每次会话结束都 taskkill 游戏**（用户明确批评过）——要一步步走、保持常开。
- **鼠标注入的坑（用户两次纠正后才搞对）**：
  原版自绘光标的热点是**指尖**不是整只手；`SetCursorPos` 指定点与游戏认定的命中点有偏移。
  实测菜单层 **dx=+40 / dy=+13** 才点得中。省事的做法是**扫描法**：
  `r6_drive.py scan`（横扫）/ `scany`（纵扫）逐点点击 + 帧差分判断是否生效，让数据自己说话。
- 用**截图差分**标定光标位置会被按钮 hover 高亮污染包围盒，得出错误结论——别再用这招。

### 翻过的车（别再犯）

- `var tex := null` 在 GDScript 里**直接编译不过**（无法从 null 推断类型）→ 必须 `var tex: Texture2D = null`。
- `load()` 的返回值要显式接 `Resource` 再 `is Texture2D` 判断，别直接 `:=` 到 Texture2D。
- `node.get_node("X") as MeshInstance3D` 才安全；直接赋给 `: MeshInstance3D` 变量会踩类型检查。
- 地形平面用**自建 ArrayMesh**（4 顶点 + 显式 UV），不要猜 `PlaneMesh` 的 UV 朝向：
  `u = x/S + 0.5`、`v = 0.5 - z/S`，配合 `CULL_DISABLED` 万无一失。
- 相机取景的**真实答案**：原版不是俯视全盘，而是**跟着角色、约 3~4 格远**的近距低机位
  （一屏只见 4~5 块地毯）。第一版我按"框住全盘"摆，完全不对。
  验收时必须同时出「跟随」与「全盘（Tab）」两种图。
- 一块面板里放 `Control` 子类（Minimap）会自动铺满内容区，尺寸靠父容器给。

### BGM —— 实测（标记音替换 + 回环录音 + FFT）

- 方法：把 18 首 MP3 换成 **100 s** 纯音标记（420/460/…/1100 Hz 步长 40），
  副本 `F:/游戏/Rich6bgm` 里**只放 `.wav` 不放 MP3** ——
  exe 的 BGM 格式串是 `%ssound\music\m%.5d.wav`，引擎按扩展名试探，`.wav` 被优先命中。
- **结论**：菜单/大厅 = **m01001**（420 Hz）；**7 张地图的对局曲全是 m01009**（740 Hz，8/8 命中）。
  **地图不参与选曲**。
- **引擎不是单曲循环**：一曲放完自动接下一首（12 s 标记时每 12.0 s 精确换一首；
  100 s 标记时残留实例从 740→780 = `m01009`→`m01010`，是 +1）。
  → 新增 `Audio.play_bgm_playlist()`（顺序 `m01001…m01018` 放完回卷、单曲不循环）。

# 第二轮：老板实机反馈「地毯与石子路完全没对齐」→ 根因修复 + 改 94 格

## 一、根因（**不是格数问题**）

`game/scripts/ui/board_view.gd` 的 `_build_ground()` 里地面 UV 写成 `v = 0.5 - z / S`
→ **整张地形贴图沿 Z 轴镜像**。而 `aiji_tilepos.json` 的映射是 `py = (z/S + 0.5)×1024`
（与 z 同向）。因为路线是**闭合环且围绕棋盘中心**，「旋转 180°」与「Z 镜像」在环上
**几乎等价** → 症状不是明显翻转，而是「形状对、整体错开 ≈2 格」。
已改成 `v = z / S + 0.5`。

## 二、同源坑：`minimap.gd::_uv()` 也有 `0.5 - w.y/b`（已一并修）

新工具 `tools/check_minimap_uv.py`。⚠️ **HUD 小地图是被重画过的美术**（蓝河 vs 干河床），

## 十、UI 对齐（议题 39~42）—— 老板定了新优先级

老板原话：**「先优先对齐UI吧，然后再放入真实的角色模型，然后再接入卡牌系统」**
→ 三项优先级：**① 对齐 UI → ② 真实角色模型（`actor/`）→ ③ 卡牌系统（`card/`）**。本轮做 ①。

### 1. 两个「旧结论是错的」被推翻

**(a) 「原版 UI 面板全是程序绘制」—— 只对顶栏底条成立。**
上一轮只翻了 `uitex/other/` 就下了结论。这次把 **`uitex/` 全部 17 个子目录列了一遍**，
发现现成贴图一直躺着：

| 部件 | 原版素材 |
|------|---------|
| 左下角色面板底框 | `uitex/other/atb.png`（256×128，**主框 176×123**，纯平色） |
| 右下 6 个图标按钮 | `uitex/subc/{电视,股票,地图,聊天,话筒,min}.png`（32×32） |
| **GO 气泡**（掷骰子入口） | `uitex/labar/go.png` / `go_dn.png` |
| 落点气泡的是/否 | `uitex/other/{yes,no}_{up,dn}.png`（**已带中文「是」「否」**） |
| 头顶圆盘 / 骰子 / 骰子动画 | `uitex/labar/{背景.png, 骰子.png, anim.png(16 帧)}` |

**教训**：**下结论前先把目录摆开。** 只搜一两个子目录就断言「包里没有」代价很大。

**(b) 原版真字体破了。** `gbdata/unicode16.tft` / `unicode24.tft` = **TNFT 点阵**
（`"TNFT"` + 版本 + 字高 + `u32 65536` + 65536×ceil(px/8)×px 字节 1bpp 固定字框）。
**文件大小精确校验**：16px → 2097172 B、24px → 4718612 B ✓。
→ `tools/r6_tft.py` 转 BMFont → `game/assets/fonts/r6_16|24.{fnt,png}`，
设成 `Window.theme.default_font` → **全部中文都是原版点阵字**。
⚠️ **顶栏数字是另一套**：`uitex/other/number1.tga`（粗体白字 + 深蓝描边）；
用真字体（细笔画）会像"马赛克描边"。实测墨迹高 17.1、字距 3.4、横向 ×1.38。

### 2. 度量口径（写死在 `app.gd` 注释里）

```
原版 1024×768（4:3）；实机截图 07_牌桌.png = ×1.5（1536×1152）
我们 1280×720（16:9）→  UI_SCALE = 视口高 / 768  = 0.9375；截图 px ÷ 1.5 = native
```
⚠️ 4:3 → 16:9 会让 HUD **占屏比变小**，这是**正确行为**，别为"占屏比一致"单独拉伸宽度。

### 3. 四个 HUD 模块 + 动作气泡

- **顶栏**（议题 40）：程序生成竖向渐变底条（stops 逐行采样）+ 5 个「胶囊图徽 + 数字」+
  `x/y` 面板 + 右侧 3 图标条。控件 `hud_number.gd`。
- **左下角色面板**（议题 41）：直接用 `atb.png` 底框，**按平色精确分割 6 个槽位**
  （`avatar[10,9,73,73] info[93,10,64,64] name[12,86,69,14] stat[91,79,69,14]
  bar_a[9,103,76,14] bar_b[90,103,76,14]`，frame 内像素），叠大圆头像 `roleN_01` + 名字 +
  血量黄条 + 左下角齿轮按钮。显示 220×149.3 native。
- **右侧头像列**（议题 41）：**贴在右边缘的竖排圆头像**（`roleN_21`，原版**没有底板**），
  右距 2.0 / 顶 216.7 / 35.3×42 / 步距 52；当前行动者描亮边、出局者压灰。
- **右下小地图框 + 图标条**（议题 42）：框按原版配色自绘（浅蓝白描边 + 深蓝底）；
  6 图标 = `subc/*.png`（显示 35 native、步距 41.8）。
- **动作入口改原版形态**（议题 42b）：原版**没有常驻按钮条** ——
  **掷骰子 = 角色头顶 GO 圆钮**、**买地/升级 = 角色头顶落点气泡（是/否）**。
  铁律「一次性机会」照旧（有机会时不给 GO）。

### 4. ⭐ 小地图铺法定案（血泪）

### 5. 三个踩过的坑（都已写进 README / MEMORY）

1. **气泡定位必须锚世界点再投影**：第一版用「角色屏幕位置 + 固定屏幕像素抬升」→
   气泡压在角色身上 / 随相机远近飘。改成

## 十一、UI 对齐复审：三处「看着像做了、其实不对」的修掉

老板的 ① 号任务（UI）在收尾复审时发现三处**视觉上看着完成、实际与原版不符**的问题。
指令仍是 *「先优先对齐UI，然后再放入真实的角色模型，然后再接入卡牌系统」*。

### 1. ⭐ GO 钮其实是**两张贴图叠出来的**（推翻「只用 `labar/go.png`」）

原版角色头顶那颗 GO 不是一张图：**`labar/背景.png`（深蓝球）打底 + `labar/go.png`（青球 GO）
叠在偏右上**。单独用任一张都不对 —— 两张**都是贴边裁切的残图**：

| 素材 | 尺寸 | 可见区 alpha bbox |
|------|------|------------------|
| `labar/背景.png` | 64×64 | `(0, 3, 64, 64)` —— 左右贴边，直径就是 64 |
| `labar/go.png` / `go_dn.png` | 64×64 | `(0, 10, 41, 64)` —— **左侧被裁**（"G" 缺一竖） |

**因为都贴边，不能按画布对齐，只能按「可见区中心」对齐。** 参数从原版实机
`docs/screenshots/orig/08_牌桌_2.png` 按颜色分离量得（截图 = native 的 1.5 倍）：

- 蓝球直径 ≈ **73.3 native** → 贴图 64 缩放 **×1.146**
- 青球可见区中心 比 蓝球可见区中心 偏 **(+13.7, +1.0) native**

→ `tools/make_panel_ui.py::_compose_go()` 合成 `go_btn.png` / `go_btn_dn.png`（78×78 native）；
`app.gd::UI_GO_SIZE` 42.7 → **78.0**。原版 GO 旁那颗**实体骰子**是 `labar/骰子.png`
（我们走 3D `Sprite3D`），**不是**这张合成图的一部分。
（顺手核对：`go.tga` 的 TGA 头 `desc=0x08` → 无 RTL、底向上，PIL 解码正确 —— 不是解码错。）

### 2. 是 / 否 = **两块半胶囊拼一整颗**

`yes_up.png` / `no_up.png` 都是 64×32、**可见区只有左边 56×32**（右 8px 全透明）；
`yes` 只有**左**圆头、`no` 只有**右**圆头 → 并排贴紧才是原版那颗「是│否」胶囊。
之前 `KEEP_ASPECT_CENTERED` + 40×20 native + 8px 间距 → 屏幕上两颗**半胶囊各自为政**
（直切口外露）。现在：`AtlasTexture.region=(0,0,56,32)` 裁透明边 + `separation=0` +
`STRETCH_SCALE` + 56×32 native。
⚠️ **未考证**：原版把这两块画多大（翻遍 `docs/screenshots/orig/` 没找到带买地提示的截图）
→ 已登记 `docs/ui-audit.md §8`。

### 3. ⭐ `--uishot` 的两个坑（「GO 钮明明 visible 却没画出来」）

1. **不能按固定时刻拍**：开局头几秒角色还在「入场」状态（`me.moving != 0`），
   `_sync_action_entry()` 此时把 `_go_btn.visible` 置 **false** —— 3.0 秒硬拍只能拍到头上那颗骰子。
   → 改成**等 `_go_btn.visible` 真为真**再拍（8 秒兜底 + `push_warning`）。
2. **`_capture()` 是协程，必须 `await` 它之后才改游戏状态**：它内部
   `await RenderingServer.frame_post_draw` 才去 `get_viewport().get_texture()`。
   原代码 `_capture(...)` 没 await 就紧跟 `Net.send_action("roll")` → 角色先动起来、
   下一帧把 `_go_btn.visible` 置回 false → **真正抓帧时按钮已经没了**。
   症状极迷惑：临时打印 `get_global_rect()` 完全正确、`texture_normal` 也非空，图里却空无一物
   —— 差点去查 CanvasLayer 绘制顺序。

### 4. 顺手清理死代码

`app.gd`：`var _hud_tile: Label`、`func _hex_to_color()`（无调用者）、
`func _dice_texture()`（骰子贴图由 `board_view.gd` 直接加载）。
另修 `docs/ui-audit.md` 里 25 处 `uittex` 拼写（应为 `uitex`）。
