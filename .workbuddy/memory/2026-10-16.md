## 打通 Ghidra（绕开 REA）

**REA 仍然不可用**（不是配置问题）：
- 设好 `GHIDRA_INSTALL_DIR` / `JAVA_HOME` 后，`rea doctor` 里 Ghidra 的 **8 项检查全 true**
- 但 `decompile` / `analyze` 报 `unsupported_host`：
  `REA Windows native controls are unavailable: Delete owned object by handle failed (Win32 5)`
  → **REA 靠 Windows Job Object 托管子进程，那个能力探测在本机失败**。
  加 `dangerouslyDisableSandbox` 也一样 → **大概率是安全软件拦「进程托管/句柄删除」**，
  不是沙箱。
- ⚠️ **陷阱**：`doctor` 的 `ghidra: ok: true` **只证明静态配置对**，分析时的 native probe 才决定能不能跑。
  **别把 doctor healthy 当成「能跑」。**

**改用 Ghidra headless 直接跑**（能力等效，REA 底层就是调它）：
```bash
export JAVA_HOME='C:/Users/12733/AppData/Local/Programs/Java/jdk-25.0.4.1+1'
G="C:/Users/12733/AppData/Local/Programs/Ghidra/ghidra_12.1.4_PUBLIC"
"$G/support/analyzeHeadless.bat" <proj> Rich6 -import <exe> -noanalysis -log <log>
"$G/support/analyzeHeadless.bat" <proj> Rich6 -process rich6.exe \
  -postScript ExportFunctionInfoScript.java <out> -log <log>
```
**完整分析只用了 1 分 10 秒**。

### ⚠️ 三个坑（都会误判成「工具坏了」）
1. **Ghidra 拒绝路径里以 `.` 开头的元素**：`Path element starting with '.' is not permitted`。
   我最初用 `.workbuddy/ghidra_proj` → 直接被拒。**项目目录只能叫 `ghidra_proj/`**。
2. **失败时终端可能完全无输出**：错误只进 `-log` 指定的文件 → **必须带 `-log` 并读它**。
3. **bash 里别给 `.bat` 套嵌套引号**（`cmd //c ""...bat" "arg""` 会静默失效）→ 直接调 `.bat`。
